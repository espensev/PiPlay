## Executive verdict

b25 is a narrow P1 patch on top of b24. It does two meaningful things:

1. Shrinks the visible WebView resize inset from **10 DIP** to **4 DIP** in both the main window and the popout.
2. Removes the prompt dialog's remaining **1px inner border**.

That is progress. It directly addresses the strongest remaining b24 complaint: the video looked like it was sitting inside a thick black tray. b25 should look cleaner than the screenshots you posted.

But b25 does **not** change the overall verdict from the previous review:

> PiPlay is cleaner than b22 and b24, but it is still not yet the clean rounded floating media-player target.

The remaining problems are now mostly product/architecture issues, not one-line border fixes:

- The WebView still needs a **4-DIP owned edge band** for resize because the WebView2 child HWND swallows hit testing.
- The top chrome remains a large persistent app frame in the main window.
- The popout still has a chrome strip unless auto-hide is enabled and fade is active.
- `Show popout` still only focuses the popout instead of bringing playback back.
- Return state still does not preserve popout-side paused state, volume, mute, or playback speed.
- Profile color still does not become the app accent.
- Opacity is still whole-window alpha on the popout, so it makes the video itself transparent.
- `Soft` and `Round` are still not distinct at the outer-window level.
- No Fit / Fill / Cinema Padding video-fit model exists.

The best description of b25 is:

```text
b25 = smaller border/tray patch, not a full UI target pass.
```

## Visual read against the screenshots

### Border / tray

The b24 screenshots show a cleaner app than b22, but the video still sits inside a black tray. b25 should reduce that tray because the explicit WebView band has gone from 10 DIP to 4 DIP. That is good.

However, b25 is still not literally borderless. The source explains why: the WebView2 child HWND swallows `WM_NCHITTEST`, so the top-level window has to own edge pixels for resize (`src/PiPlay/MainWindow.xaml:156-160`, `src/PiPlay/PlayerWindow.xaml:95-99`). This means the current architecture cannot reach a true zero-pixel WebView edge without either losing edge resize over the video or doing a deeper WebView2/windowing lift.

So b25 is a pragmatic compromise:

```text
10-DIP visible tray  ->  4-DIP technical edge band
```

That is better, but not the final “all OF IT” border target.

### Round / soft looks odd because the outer window cannot distinguish them

The screenshots make `Soft` and `Round` look too similar. The code explains why.

The internal radii are different:

- `soft` uses `MinimalRadii` (`src/PiPlay/Theme/ThemeCatalog.cs:127-130`, `:298-305`).
- `round` uses `SoftGlassRadii` (`src/PiPlay/Theme/ThemeCatalog.cs:132-135`, `:298-305`).

But the actual outer HWND corner mode is the same:

```csharp
"soft"  => DwmCornerMode.Round
"round" => DwmCornerMode.Round
```

That mapping is in `ThemeCatalog.DwmCornersFor(...)` (`src/PiPlay/Theme/ThemeCatalog.cs:310-317`). The tests explicitly assert it (`tests/PiPlay.Tests/ThemeCatalogTests.cs:138-147`).

So the user-visible outer silhouette cannot meaningfully differ between `Soft` and `Round`. Only the internal controls, chips, panels, and inputs get different radii. If the user judges the actual window shape, these two options will feel almost identical.

### Unused video space

There are still three sources of unused space:

1. **Legitimate aspect-ratio bars.** A 16:9 video in a non-16:9 window will create black bars in any honest Fit mode.
2. **App-caused inset/tray.** This improved from 10 DIP to 4 DIP, but it still exists by design.
3. **Normal YouTube page layout.** Since compact embed mode is disabled, the popout is mostly hosting the full YouTube watch page, not a local pure-video shell. The source forces new popouts to Normal mode while `CompactPlayerEnabled = false` (`src/PiPlay/Services/PlaybackModePolicy.cs:69-83`).

b25 only helps item 2. It does not implement a true video-fit system.

### Opacity still visibly hurts the video

The last opacity screenshot shows the video itself becoming washed out and the desktop/terminal bleeding through. That is exactly what the source does: `WindowOpacityApplier.Apply(...)` applies layered-window alpha to the top-level popout HWND (`src/PiPlay/Services/WindowOpacityApplier.cs:75-115`), and `PlayerWindow.ApplyWindowOpacityToHwnd(...)` applies that to the whole popout (`src/PiPlay/PlayerWindow.xaml.cs:706-716`).

This is not “chrome transparency.” It is “whole popout opacity.” The Settings UI text is honest-ish in that it says `Window opacity` and the slider tooltips say `Popout window opacity` (`src/PiPlay/SettingsWindow.xaml:218-250`), but it conflicts with the newer owner requirement that transparency should not reduce video quality.

# Detailed priority review

## P1 — Borderless surface

### What is fixed or improved

b25 has real P1 improvements:

- DWM system frame-border suppression exists via `DWMWA_BORDER_COLOR = DWMWA_COLOR_NONE` (`src/PiPlay/Services/WindowOpacityApplier.cs:141-168`).
- Main, popout, Settings, and prompts call that suppression path (`src/PiPlay/MainWindow.xaml.cs:672-678`, `src/PiPlay/PlayerWindow.xaml.cs:727-733`, `src/PiPlay/SettingsWindow.xaml.cs:219-227`, `src/PiPlay/Prompt.cs:45-53`).
- High Contrast keeps the system border, which is the right accessibility exception (`src/PiPlay/Services/WindowOpacityApplier.cs:170-172`).
- Main and popout WebView margins are now 4 DIP, not 10 DIP (`src/PiPlay/MainWindow.xaml:161-165`, `src/PiPlay/PlayerWindow.xaml:100-104`).
- Settings outer border is zero (`src/PiPlay/SettingsWindow.xaml:83`).
- Prompt inner border is now zero (`src/PiPlay/Prompt.cs:89-94`).
- Resting button/textbox borders are transparent, while focus ring behavior is preserved (`src/PiPlay/Theme/ControlStyles.xaml:25-67`, `:228-255`).
- The profile combo closed-state toggle border is transparent (`src/PiPlay/Theme/ControlStyles.xaml:382-384`).

This is all directionally correct.

### What still blocks P1 from being “done”

#### 1. The WebView edge band still exists

The 4-DIP band is smaller, but it is still a visible layout inset. The app still has this contract:

```text
ResizeBorderDip = WebView left/right/bottom margin = WindowChrome resize thickness
```

That is tested directly (`tests/PiPlay.Tests/Ui/XamlInvariantTests.cs:65-78`). It is also documented as structurally required because the WebView2 child HWND swallows hit testing (`src/PiPlay/MainWindow.xaml:156-160`, `src/PiPlay/PlayerWindow.xaml:95-99`).

This means b25 does not remove “all of it.” It shrinks the visible border/tray to the cheapest practical value under the current architecture.

#### 2. The 4-DIP side resize target may feel too thin

The previous 10-DIP band was visually ugly but easy to grab. b25 keeps the corner grab generous at 32 DIP (`src/PiPlay/Services/BorderlessResizeHitTestPolicy.cs:9-10`), but the cardinal side resize area is only 4 DIP. That is probably acceptable for power users, but it may feel fiddly at 100% DPI and on touchpads.

This is a UX tradeoff:

```text
10 DIP = easier resize, ugly tray
4 DIP  = cleaner look, thinner side-resize target
0 DIP  = target look, but needs deeper window/WebView work
```

#### 3. Internal separators still read as lines

P1 is primarily about the outer border, but the Settings footer still draws a top hairline (`src/PiPlay/SettingsWindow.xaml:267-270`), preset chips use borders (`src/PiPlay/SettingsWindow.xaml:46-75`), and dropdown popups still use `BorderSubtle` (`src/PiPlay/Theme/ControlStyles.xaml:418-422`). These are not the same severity as the old outer border, but in a “border visibility effectively zero” target they still contribute to the framed feel.

#### 4. The main window still presents as an application frame, not a floating media surface

The main window has fixed 42-DIP titlebar and 50-DIP toolbar rows (`src/PiPlay/MainWindow.xaml:31-36`). Even with no border, it still reads as a browser shell. That may be fine for the main browsing window, but it does not match the floating rounded-player reference.

### P1 verdict

b25 improves P1 substantially. It should be accepted as a useful patch, but P1 should not be closed if the target is truly:

```text
No visible outer frame.
No visible WebView gutter.
No tray/double-frame feel.
Clean rounded floating media surface.
```

The next P1 decision is architectural:

- keep 4 DIP as the practical current-HWND compromise; or
- invest in a deeper WebView2/windowing solution so resize can work without a visible owned edge band.

## P2 — Profile color as global accent

This is still not implemented.

The current source intentionally keeps profile color as identity-only:

- `ProfileAccentService.ResolvedAccentColor(...)` always returns the global app accent, not the active profile color (`src/PiPlay/Services/ProfileAccentService.cs:12-13`).
- `ProfileAccentService.CommitAccent(...)` writes to `settings.Theme.AccentColor`, not to the active profile (`src/PiPlay/Services/ProfileAccentService.cs:38-42`).
- Main-window profile tests assert that selecting a profile does not recolor the app accent (`tests/PiPlay.Tests/Ui/MainWindowProfileAccentTests.cs:12-39`).
- Service tests assert `Resolved_accent_always_uses_global_app_accent` (`tests/PiPlay.Tests/ProfileAccentServiceTests.cs:9-19`).
- The profile selector chip itself uses the profile color as a local identity fill (`src/PiPlay/MainWindow.xaml:101-106`).

This was a deliberate earlier design, but it conflicts with the current owner direction:

```text
Profile color should do more than one button.
The selected profile color should replace the default blue/accent throughout the UI.
```

The priority doc itself labels this as a conflict/reversal (`docs/PiPlay_UI_Priority_Improvements.md`, P2 section). The code has not followed that new direction yet.

### Required P2 change

Change the model from:

```text
profile color = profile chip only
app accent = global Settings accent
```

to a configurable or owner-selected model such as:

```text
Accent source:
- App accent only
- Active profile color when available, otherwise app accent
```

For the current requested direction, the default should likely be:

```text
Active profile color when available, otherwise app accent
```

Then `ResolvedAccentColor` should use the active profile's `AccentColor` when present, and the following should recolor together:

- profile selector / selected chip
- primary buttons
- play button
- popout button
- pin/fade active states
- focus ring / active outlines
- popout controls
- placeholder icon/button

### P2 verdict

Not done. This remains a clear mismatch against the current priority list.

## P3 — Transparency / opacity scope

P3 remains mostly unchanged from the b24 review.

Current behavior:

- Opacity is stored as active/idle window opacity values (`src/PiPlay/Models/AppSettings.cs:68-82`, `:120-124`).
- Settings exposes active and idle sliders under `Window opacity` (`src/PiPlay/SettingsWindow.xaml:218-250`).
- The feature applies to the popout only; `MainWindow` only forwards opacity values to `_player` (`src/PiPlay/MainWindow.xaml.cs:526-535`, `:685-689`).
- The applied mechanism is whole-window layered alpha (`src/PiPlay/Services/WindowOpacityApplier.cs:75-115`).

There is no setting for:

```text
Transparency scope:
- Off
- Main only
- Popout only
- Both
```

There is also no separation between:

```text
chrome/background transparency
video opacity
whole-window opacity
```

### Why the current opacity model fails the visual target

The source applies opacity to the top-level popout HWND. WebView2 video is inside that top-level window, so it becomes transparent too. That is why the opacity screenshot looks foggy and washed out.

Soft Glass defaults are now subtle — active 0.97 and idle 0.90 (`src/PiPlay/Theme/ThemeCatalog.cs:226-237`) — which is much better than heavy translucency. But the model still permits obvious video degradation, especially via manual settings or lower slider values.

### Required P3 change

At minimum, rename the current feature honestly:

```text
Whole popout opacity
```

Then add the real target as a separate future feature:

```text
Transparency scope: Off / Main / Popout / Both
Transparency target: Chrome/background only by default
Video opacity: 100% unless explicitly changed
```

A true desktop-see-through chrome layer may require a deeper composition/DWM/acrylic architecture because the current non-layered WPF window plus WebView2 HwndHost has hard airspace constraints. If that lift is deferred, do not present the current feature as the final transparency model.

### P3 verdict

Partial infrastructure exists, but it is the wrong semantic shape for the owner requirement. The current opacity feature should be treated as an advanced whole-window effect, not final transparency.

## P4 — Popout button must bring video back

This is still not done, and it is more serious than just the label.

### Current behavior

The primary action and placeholder still focus the popout:

- Placeholder click handler calls `ActivateExistingPlayer()` only (`src/PiPlay/MainWindow.xaml.cs:781-784`).
- `StartVideoPopoutAsync()` returns early to `ActivateExistingPlayer()` if a popout already exists (`src/PiPlay/MainWindow.xaml.cs:786-790`).
- `ActivateExistingPlayer()` restores/minimizes and activates the existing popout (`src/PiPlay/MainWindow.xaml.cs:869-880`).
- The button state is explicitly `Show popout` with tooltip “Bring the open Video Popout to the front” (`src/PiPlay/MainWindow.xaml.cs:889-897`).
- The XAML placeholder button content is still `Show popout` (`src/PiPlay/MainWindow.xaml:185-189`).
- Tests pin the focus-only action (`tests/PiPlay.Tests/Ui/XamlInvariantTests.cs:257-268`, `tests/PiPlay.Tests/Ui/WpfRuntimeTests.cs:657-690`).

This directly conflicts with the requested behavior:

```text
Button should bring the vid back.
Otherwise it is wasted.
```

### Existing return-on-close is useful, but not enough

There is already a return path when the popout closes:

- `PlayerWindow` raises `PlayerClosed` with `PlayerReturnState` (`src/PiPlay/PlayerWindow.xaml.cs:83-84`, `:859-866`).
- `MainWindow.Player_OnClosed` hides the placeholder and calls `ApplyReturnActionAsync(...)` (`src/PiPlay/MainWindow.xaml.cs:940-960`).
- `ReturnPolicy` decides seek/play/navigate (`src/PiPlay/Services/ReturnPolicy.cs:24-48`).

So the app has most of the plumbing needed for “Bring video back.” The missing part is making the main button intentionally trigger that return path.

### Bigger issue: paused state is not preserved correctly

The current return behavior preserves whether the **source** was playing when the popout started, not whether the **popout** is playing/paused when it returns.

At popout start:

```csharp
_sourceWasPlayingAtPopout = state is { Paused: false };
```

That is in `MainWindow.StartVideoPopoutAsync()` (`src/PiPlay/MainWindow.xaml.cs:798-801`). On return, `ReturnPolicy.Decide(...)` uses `_sourceWasPlayingAtPopout` (`src/PiPlay/MainWindow.xaml.cs:983-1006`). `PlayerReturnState` has no `Paused` field (`src/PiPlay/Models/PlayerReturnState.cs:8-27`), and `YouTubeDomBridge.PlayerState` has no volume/mute/speed fields (`src/PiPlay/Services/YouTubeDomBridge.cs:6-31`).

Consequence:

```text
If the source was playing when popped out,
and the user pauses in the popout,
then closing/returning can resume playback anyway.
```

That violates the new requirement to preserve playing/paused state.

### Missing state for full P4 acceptance

The owner requirement says preserve:

- timestamp
- playing/paused state
- volume
- mute
- playback speed
- playlist position

Current state preserves only:

- timestamp, approximately via polling (`src/PiPlay/PlayerWindow.xaml.cs:461-476`)
- returned video id in some navigation cases (`src/PiPlay/PlayerWindow.xaml.cs:296-306`, `:328-339`)
- window topmost/fade/placement (`src/PiPlay/Models/PlayerReturnState.cs:21-26`)

It does not preserve:

- current paused state in the popout
- volume
- mute
- playback rate
- playlist position beyond a video-id/navigation fallback

### Required P4 change

Add a true dock/undock command:

```text
When no popout exists:
  Pop out video

When popout exists:
  Bring video back
```

Implementation direction:

1. Add a `BringVideoBackAsync()` path in `MainWindow`.
2. Add a `CaptureReturnStateNowAsync()` method on `PlayerWindow` so the return button does not rely only on the last 250ms polling tick.
3. Extend return state with at least `Paused`, `Volume`, `Muted`, and `PlaybackRate`.
4. Make `ApplyReturnActionAsync(...)` use the popout's current paused state, not `_sourceWasPlayingAtPopout` alone.
5. Keep `Show popout` as secondary behavior only if needed, not the primary placeholder action.

### P4 verdict

Not done. This should be the next functional priority after the border/tray patch.

## P5 — Video area utilization

b25 helps this only indirectly by reducing the WebView inset from 10 to 4 DIP. It does not implement the requested viewing model.

### Current state

- Popout WebView margin is now 4 DIP (`src/PiPlay/PlayerWindow.xaml:100-104`).
- Popout chrome strip is 32 DIP when visible (`src/PiPlay/PlayerWindow.xaml:36-66`).
- The strip can collapse only when strip auto-hide is enabled and fade is active (`src/PiPlay/PlayerWindow.xaml.cs:608-624`, `:673-681`, `:823-832`).
- New popouts force Normal YouTube watch-page mode while Compact is disabled (`src/PiPlay/Services/PlaybackModePolicy.cs:69-83`).
- There is no `VideoFit` setting in `AppSettings` (`src/PiPlay/Models/AppSettings.cs:46-97`).
- There are no Fit / Fill / Cinema Padding controls in Settings (`src/PiPlay/SettingsWindow.xaml:195-263`).

### Why this matters

The screenshots show too much unused black area around video. Some of that is valid aspect-ratio letterboxing. Some is PiPlay chrome/inset. Some is YouTube's own page layout. The product needs to distinguish these instead of treating all black space as equivalent.

The current behavior is closer to:

```text
Fit inside current WebView/page/tray
```

The target is:

```text
Fit window by default
Fill/crop optional
Cinema padding optional
```

### Normal YouTube page mode is not enough for “video player” feel

Because Compact mode is currently dormant (`CompactPlayerEnabled = false`), the popout is not a dedicated player shell. It is a normal YouTube watch page in a borderless browser window. That makes it hard to guarantee maximum video use without either:

- injecting layout/theater/fullscreen behavior into the YouTube page;
- reintroducing a local shell that is reliable for embed-disabled videos; or
- adding a normal-mode “video-first” DOM mode that hides or minimizes YouTube chrome where allowed.

Also note that normal-mode fullscreen element events are intentionally ignored (`src/PiPlay/PlayerWindow.xaml.cs:543-553`). If the YouTube player's own fullscreen path is expected to drive popout expansion or immersive behavior, that gate may need to be revisited.

### Required P5 change

Add a real video-fit model:

```text
Video fit:
- Fit window       default
- Fill / crop      optional
- Cinema padding   optional
```

Then make `Fit window` use the maximum available content region, not the current padded/tray page feeling.

### P5 verdict

Slightly improved by P1, but still not implemented as a product feature.

## P7 — Rounded corner system

P7 remains partial and unchanged from b24.

### What works

The app consistently applies DWM corner preferences and suppresses the DWM frame border:

- `WindowOpacityApplier.SetCornerMode(...)` maps to `DWMWA_WINDOW_CORNER_PREFERENCE` (`src/PiPlay/Services/WindowOpacityApplier.cs:117-139`).
- Main, popout, Settings, and prompts apply native corner mode (`src/PiPlay/MainWindow.xaml.cs:672-678`, `src/PiPlay/PlayerWindow.xaml.cs:727-733`, `src/PiPlay/SettingsWindow.xaml.cs:219-227`, `src/PiPlay/Prompt.cs:45-53`).

### What does not work

The corner UI promises more distinction than DWM can deliver.

Settings offers:

```text
Theme / Square / Small / Soft / Round
```

But the actual outer modes are only:

```text
Square      -> DWM Square
Small       -> DWM SmallRound
Soft        -> DWM Round
Round       -> DWM Round
Theme       -> preset default
```

This is hard-coded in `ThemeCatalog.DwmCornersFor(...)` (`src/PiPlay/Theme/ThemeCatalog.cs:310-317`).

The result is exactly what the screenshots suggest: `Soft` and `Round` can look nearly identical at the outer edge.

### Recommended P7 decision

Short term, rename the outer-window corner choices to the real native modes:

```text
Default / Square / Small / Round
```

Then treat `Soft Glass` as a theme/preset, not a separate outer-corner shape.

Long term, only expose `Medium` or `Large` if the app actually has a custom rounded-card architecture that produces visibly different outer radii. DWM-only cannot give a real 18/22/32-DIP custom outer radius.

### P7 verdict

Partial. The current implementation is technically coherent, but the UI language overpromises.

## P8 — Unified main and popout experience

b25 is visually more unified than b22, but the main and popout are still not one coherent appearance/behavior system.

### What is unified

- Both windows use the same theme resources.
- Both windows get DWM frame-border suppression.
- Both windows use the same resolved app accent when the global accent changes (`src/PiPlay/MainWindow.xaml.cs:639-645`, `:685-689`).
- Corner mode is applied to both main and popout (`src/PiPlay/MainWindow.xaml.cs:672-689`).

### What is not unified

- Profile colors do not drive the global accent.
- Opacity applies only to popout, not main.
- Opacity applies to the video itself.
- Popout auto-hide exists, main auto-hide does not.
- Popout can be focused from the placeholder, but not docked back from the placeholder.
- Video fit is not shared or explicit.
- The main window is a browser shell; the popout is a borderless watch-page shell; neither reaches the pure rounded media surface consistently.

### P8 verdict

Partial. The theme resources are shared, but the user-facing behavior is not yet unified.

The new prompt-shell test is exactly the kind of regression guard P1 needed (`tests/PiPlay.Tests/Ui/WpfRuntimeTests.cs:1261-1269`).

## Tests still pin behavior that conflicts with the current owner direction

These tests are useful for the current codebase but must be rewritten when the owner direction is implemented:

- `Source_placeholder_has_show_popout_action` pins `Show popout`, not `Bring video back` (`tests/PiPlay.Tests/Ui/XamlInvariantTests.cs:257-268`).
- `Popout_action_state_flips_label_tooltip_and_uia_name_together` pins focus-only copy (`tests/PiPlay.Tests/Ui/WpfRuntimeTests.cs:657-675`).
- Profile accent tests assert active profile does not recolor the app (`tests/PiPlay.Tests/Ui/MainWindowProfileAccentTests.cs:12-39`, `tests/PiPlay.Tests/ProfileAccentServiceTests.cs:9-35`).
- Corner tests assert `soft` and `round` both map to DWM Round (`tests/PiPlay.Tests/ThemeCatalogTests.cs:138-147`).
- `Grey_border_tokens_are_quieted_to_a_faint_hairline` still preserves the old “faint hairline” vocabulary (`tests/PiPlay.Tests/Ui/XamlInvariantTests.cs:919-932`).

These are not bad tests. They are accurate for the current implementation. But they now encode decisions that conflict with the latest requested UI target.

## Documentation state

The b25 changelog is unusually honest and useful. It says P1 reads cleaner but is not finished because of top chrome, separators/hairlines, letterboxed tray, and `soft`/`round` both mapping to DWM Round (`docs/CHANGELOG.md:7-24`). That matches this review.

There is a historical contradiction: the b24 changelog says v0.7.1 “completes P1” (`docs/CHANGELOG.md:26-40`), while b25 says P1 is not finished. That is acceptable historically, but if these docs are used by agents, the b25 statement should be considered the current truth.

# Highest-value next implementation order

## 1. Implement `Bring video back`

This is now the biggest functional miss.

Change:

```text
Show popout
```

to:

```text
Bring video back
```

when a popout exists.

Required source changes:

- Replace `ActivateExistingPlayer()` as the primary existing-popout action.
- Add `BringVideoBackAsync()` in `MainWindow`.
- Add a popout method to capture fresh return state before closing.
- Extend `PlayerReturnState` and `PlayerState` to carry paused/volume/mute/playbackRate.
- Update tests that currently pin `Show popout`.

Acceptance:

```text
Open video -> pop out -> pause in popout -> bring back -> main is paused at same time.
Open video -> pop out -> keep playing -> bring back -> main plays at same time.
Change volume/mute/speed -> bring back -> main preserves it where YouTube permits.
Click recommendation in popout -> bring back -> main navigates to the returned video, not the old one.
```

## 2. Decide whether 4 DIP is “good enough” or escalate P1

b25 likely makes the border much less ugly. The next step should be visual QA, not another blind code tweak.

If 4 DIP still reads as a border/tray, the next options are:

- child-HWND hit-test forwarding/subclassing for WebView2 edges;
- a WebView2 composition/windowless architecture;
- or accepting a visible technical edge but making it explicitly part of a “Cinema padding” style.

Do not reduce to 0 in XAML without preserving resize behavior.

## 3. Fix opacity semantics

Either rename the current feature to:

```text
Whole popout opacity
```

or implement the true scope/target model:

```text
Scope: Off / Main / Popout / Both
Target: chrome/background only
Video: opaque by default
```

Do not market whole-window alpha as video-safe transparency.

## 4. Resolve the profile-accent conflict

The current roadmap says profile color should become the global accent, but the current code/tests preserve the v0.6 identity-only model. Pick one.

Given the owner feedback, implement:

```text
active profile color -> resolved app accent
fallback -> global app accent
```

Then update `ProfileAccentService`, `MainWindowProfileAccentTests`, and Settings/profile edit copy.

## 5. Rationalize corner choices

The current `Soft` / `Round` distinction is too subtle at the outer edge because both map to DWM Round. Either:

- rename to native modes, or
- build a real custom-card architecture later.

Do not keep promising large/medium outer differences that the HWND cannot display.

## 6. Add video fit modes

Once popout return and P1 are stable, add:

```text
Fit window
Fill / crop
Cinema padding
```

Do this as an explicit viewing model, not by guessing from window size.

# Suggested issue list

## P0 / P1 carry-over — Verify b25 border visually

**Problem:** b25 shrinks the tray to 4 DIP but may still read as a border.

**Acceptance:** At 100%, 125%, and 150% DPI, in active and inactive states, the main and popout windows do not show a grey or double border. Any remaining black edge must read as video letterbox/canvas, not an app frame.

## P1 follow-up — Preserve resize without visible gutter

**Problem:** WebView edge margin is still the visual resize band.

**Acceptance:** Edge/corner resizing works while the video is visible, but the player does not show an obvious layout gutter.

## P2 — Profile color drives real accent

**Problem:** Profile color still only fills the identity chip.

**Acceptance:** Selecting a profile with an accent color updates the main accent resources and the open popout immediately.

## P3 — Split opacity scope and target

**Problem:** Whole-window opacity makes video transparent.

**Acceptance:** User can choose main/popout/both/off, and video remains fully opaque by default.

## P4 — Bring video back

**Problem:** `Show popout` is a focus-only action and leaves the main window as dead space.

**Acceptance:** One click returns playback to the main window with timestamp, play/pause, volume, mute, and speed preserved.

## P5 — Video fit modes

**Problem:** Popout still feels like a watch page or tray, not a dedicated player.

**Acceptance:** Fit Window uses the maximum available content area; Fill crops; Cinema Padding is opt-in.

## P7 — Honest corner model

**Problem:** `Soft` and `Round` outer corners look the same.

**Acceptance:** Either rename them to the real DWM modes or implement real custom radii.

## Bottom line

b25 is a good P1 cleanup patch. It should look better than b24 because the worst black inset was reduced from 10 DIP to 4 DIP and the prompt inner border is gone.

But this is not a full solution to the owner UI target. The current product still has a browser-frame feel, a technical edge band, focus-only popout action, whole-window opacity that degrades video, and a corner UI that overstates what DWM can do.

The next build should not spend more time only shaving pixels. The best next move is:

```text
1. Make Bring video back real.
2. Verify whether 4 DIP is visually acceptable.
3. Stop whole-window opacity from being treated as final transparency.
4. Make profile color drive the actual app accent.
```
