## Focus-area findings

### §4.1 Inset / band consistency — VERIFIED

All four moved values resolve from the single constant `BorderlessResizeHitTestPolicy.ResizeBorderDip = 4`
and are pinned by parametrized invariant tests over **both** windows, so they cannot drift apart silently:

- `BorderlessResizeHitTestPolicy.ResizeBorderDip = 4`, `CornerLengthDip = 32` (unchanged).
- `MainWindow.xaml` / `PlayerWindow.xaml`: `WindowChrome.ResizeBorderThickness = 4`; WebView2 default
  `Margin = 4,0,4,4`; Maximized `DataTrigger` still → `Margin 0` (full-bleed).
- `XamlInvariantTests.WindowChrome_invariants_hold` (`[InlineData "MainWindow.xaml"]`,
  `[InlineData "PlayerWindow.xaml"]`) asserts `ResizeBorderThickness == ResizeBorderDip.ToString()`.
- `XamlInvariantTests.WebView_margin_gives_the_window_the_resize_band` (`Browser`, `Player`) asserts
  `Margin` contains `"{d},0,{d},{d}"` (d = `ResizeBorderDip`) **and** `"0"`, and that no direct `Margin`
  attribute overrides the style setters.

Invariant **WebView Margin (L/R/B) == `ResizeBorderDip`** holds; both are 4. Because the tests read the
constant, a future band re-tune needs no test edit and any inconsistency fails the gate.

### §4.2 Hit-test boundary semantics — VERIFIED against `HitTest`

`BorderlessResizeHitTestPolicy.HitTest` computes:

```
border  = min(ResizeBorderDip, min(width,height)/2)
onLeft  = x <  border          onRight  = x >= width  - border
onTop   = y <  border          onBottom = y >= height - border
```

So **left/top bands are exclusive at exactly `border`** (`<`) and **right/bottom zones begin at
`width-border` / `height-border`** (`>=`). The rewritten `BorderlessResizeHitTestPolicyTests` encode
precisely these semantics:

- `Resize_zones_start_exactly_at_the_configured_border`: `HitTest(Width-Band, MidY) == HTRIGHT`,
  `HitTest(Width-Band-0.1, MidY) == null`, `HitTest(Band, MidY) == null` (left edge exclusive).
- `Corner_length_boundary_is_explicit`: `nearLeftCorner = x <= corner` confirmed — `HitTest(Corner, …)`
  is the diagonal, `HitTest(Corner+0.1, …)` is the cardinal.

Every probe was hand-traced; all match. The classic off-by-one at the band edge is correctly pinned.

### §4.3 Tiny-window clamp — VERIFIED, and the test discriminates the clamp

`Tiny_windows_clamp_the_resize_band_to_half_the_window` uses a one-band window (`tiny = Band = 4`), forcing
`border = min(4, min(4,4)/2) = min(4,2) = 2` — i.e. the `dim/2` arm. The test asserts **both diagonals**:

- `HitTest(4,4, x=1, y=1) == HTTOPLEFT`, and
- `HitTest(4,4, x=3, y=3) == HTBOTTOMRIGHT`.

The bottom-right assertion is the discriminating one: at `x=3,y=3` with the clamped `border=2`,
`onTop = (3 < 2) = false` and `onBottom = (3 >= 2) = true` → `HTBOTTOMRIGHT`. If the clamp were *not* in
effect (full `border = 4`), `onTop = (3 < 4) = true` and `nearRightCorner = (3 >= 4-2) = true` would yield
`HTTOPRIGHT` instead. So the assertion can only pass when `min(Band, dim/2)` genuinely lands on the `dim/2`
arm — exactly the property the test claims to guard.

### §4.4 Prompt border removal — VERIFIED, no dead code

`Prompt.BuildShell`'s content `Border` changed `BorderThickness 1 → 0` and dropped
`BorderBrush = Brush("BorderSubtle")`; docstring updated ("a 1px border" → "no inner border"). Checked:

- `Brush(...)` (the local `(Brush)Application.Current.Resources[key]` helper, `Prompt.cs:18`) is still
  referenced 11× (`AppBackground`, `SurfaceBase`, `TextPrimary/Secondary`, `DangerPin`, …) — **not dead**
  (verified by grep, not inferred; an unused private method is a C# warning, not a build error, so the
  green gate would not have caught it).
- `"BorderSubtle"` is a shared resource key used elsewhere in the app; removing its single use here does
  not orphan it.
- New `WpfRuntimeTests.Prompt_shell_has_no_visible_inner_border` pins `border.BorderThickness == 0`.
- The zero-thickness `Border` is retained intentionally as the test's stable assertion target; with
  thickness 0 and no brush it draws nothing. Matches the already-borderless `SettingsWindow`.

The 1px → 0 change shifts inner content by 1 DIP per side — intended and visually negligible; the
`SurfaceBase` title strip + `AppBackground` body still separate the dialog from what is behind it.

## Findings

**No blocking findings.** One latent, currently-inert nit:

1. **Culture-sensitive `double.ToString()` in the XAML invariant tests (test-only; inert at integer 4;
   latent if `ResizeBorderDip` ever becomes fractional).**
   `XamlInvariantTests` compares the XAML literal against `ResizeBorderDip.ToString()`
   (`WindowChrome_invariants_hold`) and against `$"{d},0,{d},{d}"`
   (`WebView_margin_gives_the_window_the_resize_band`). Both render the `double` under the **current
   culture**, while XAML is parsed under **invariant culture**. At the present integer value `4` every
   culture renders `"4"`, so this is dormant. If the DIP ever goes fractional (e.g. `4.5`), a
   comma-decimal culture (de-DE) would render `"4,5"` / `"4,5,0,4,5,4,5"` and mismatch XAML's `"4.5"`,
   producing a **false test failure on that locale**, not a product bug.
   *Remediation (one line each):* `ResizeBorderDip.ToString(CultureInfo.InvariantCulture)` and build the
   margin string with invariant formatting. Cheap to harden now; not required for this release.
