# v0.6.0 owner-review bug log

Bugs the owner reported while reviewing the deployed Stable build (v0.6.0 b22 @ `09ee3bd`).
These are **pre-existing** unless noted — not regressions from the appearance cleanup.

## Bug 1 — Doubled audio: the source "base" keeps playing after popout

**Reported:** 2026-06-25 (owner notes it was present in earlier builds too — pre-existing, not a v0.6.0 regression).

**Symptom:** After a video pops out, the source/main window ("base") keeps playing audio in the
background ("shadow"), so the same audio plays twice (source + popout overlapping).

**Suspected mechanism:**
- On popout the source is paused exactly once, fire-and-forget:
  `src/PiPlay/MainWindow.xaml.cs:826` → `YouTubeDomBridge.PauseAsync(core)`
  (`src/PiPlay/Services/YouTubeDomBridge.cs:65-66`, a single DOM `video.pause()`).
- There is **no re-assertion** that the source stays paused for the popout's lifetime, and the source
  WebView is **not muted**. YouTube readily un-pauses itself after that single `pause()`:
  autoplay-next, an ad, or an SPA re-render.
- The popout now always loads the **full watch page (Normal mode)** — which autoplays its own audio —
  so any leak on the source side produces two concurrent streams.
- **Strong aggravator:** mix/radio sources. The repro profile "SBABATON!" is a radio
  (`...&start_radio=1`); radios autoplay the next track, which re-starts base audio after the one-shot
  pause. Most likely to double-play on radios/mixes/autoplay-on pages.

**Code touchpoints:** `MainWindow.xaml.cs:799` (capture `_sourceWasPlayingAtPopout`), `:826`
(`PauseAsync`), the auto-popout path (autoPopout=true spawned this on launch), `YouTubeDomBridge.cs`.

**Severity:** Notable audio-UX bug; pre-existing.

**Fix directions (not yet implemented — owner is cataloguing):**
- Mute the source WebView (not just pause) while a popout is active, and/or
- Re-assert pause/mute on a short guard while `_player is not null` (cover YouTube auto-resume), and/or
- Keep the source from autoplaying-next while detached.
